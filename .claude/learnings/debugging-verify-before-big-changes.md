# 큰 변경 전에 값싼 검증부터 — 개발자 지망자가 알아둘 디버깅 태도

## 2026-08-29 — tabCapture+GainNode로 아키텍처를 바꾸려다 실제로는 필요 없었던 사례

### 무슨 일이 있었나
볼륨이 계속 튀는 버그를 두고, "Web Audio GainNode가 원인일 것 같으니 `chrome.tabCapture`로 탭 오디오 자체를 가로채는 방식으로 통째로 바꾸자"는 요청이 있었다. `tabCapture`+`offscreen`+`GainNode` 조합은 실제로 구현하면 새 권한, 새 문서(offscreen document), 스트림 수명 관리까지 필요한 꽤 큰 아키텍처 변경이었다.

바로 구현에 들어가는 대신 먼저 확인한 것:
1. `tabCapture`가 정확히 어느 시점의 오디오를 캡처하는지 — 알고 보니 사이트가 이미 다 처리해서 "내보내려던 최종 결과물"을 캡처하는 것이라, 사이트가 스스로 볼륨을 들썩이게 만드는 문제 자체는 그 뒤에 배율을 곱해도 사라지지 않는다는 걸 확인.
2. 사용자의 실제 브라우저에 직접 진단 코드를 주입해서 실측 — Web Audio API(AudioContext/GainNode)는 전혀 쓰이지 않고, 순수하게 `<video>.volume` 속성만 사이트가 주기적으로 되돌린다는 걸 확인.

결론적으로 `tabCapture`는 이 버그의 해결책이 될 수 없었고, 훨씬 간단한 방식(다른 노트 [[chrome-isolated-vs-main-world]] 참고)으로 해결됐다.

### 배울 점
**"이 방법이 이론적으로 그럴듯해 보인다"와 "이 방법이 실제로 이 문제를 해결한다"는 별개다.** 특히 아래 두 조건이 겹칠 때는 구현 전에 먼저 싼 값에 검증하는 게 시간을 크게 아낀다:
- 변경 비용이 크다 (새 아키텍처, 새 권한, 여러 파일에 걸친 리팩터)
- 근본 원인에 대한 확신이 약하다 (정황 증거는 있지만 직접 확인은 안 됨)

검증 방법은 거창할 필요 없다. 이번 사례에서 쓴 건:
- 공식 문서에서 "이 API가 정확히 무엇을 하는지" 다시 확인 (추측이 아니라 명세 확인)
- 실제 환경(사용자의 진짜 브라우저)에 최소한의 코드를 직접 주입해서 몇 초짜리 실측 테스트

이렇게 몇 분 들여서 가설을 검증하고 나면, "맞는 방향으로 큰 작업을 시작"하거나 "틀린 방향임을 미리 알고 시간 낭비를 피하는" 둘 중 하나를 확실히 얻는다. 반대로 검증 없이 바로 큰 리팩터에 들어갔다면, 다 구현하고 나서야 "어? 여전히 안 고쳐지네"를 뒤늦게 발견했을 것이다.

### 실무에 적용하면
- 리뷰/설계 단계에서 "이 방법이 왜 효과가 있다고 생각하는지"를 한 문장으로 말할 수 없다면, 그건 아직 가설 단계라는 신호다.
- 재현 가능한 최소 테스트(콘솔 로그 하나, 임시 스크립트 하나)를 큰 리팩터보다 먼저 만드는 습관은, 주니어 개발자가 "일단 다 뜯어고치고 보는" 함정에 빠지지 않게 해준다.
