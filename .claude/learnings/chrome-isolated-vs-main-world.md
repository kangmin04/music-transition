# Chrome 확장의 격리된 세계(Isolated World) vs 메인 세계(Main World)

## 2026-08-29 — music-transition에서 볼륨 잠금이 안 먹히던 버그를 추적하며 (이번 프로젝트에서 가장 많은 시간을 쓴 주제)

### 무엇이 공유되고 무엇이 안 되는가
Chrome 확장의 콘텐츠 스크립트는 기본적으로 페이지 자신의 자바스크립트와는 분리된 **격리된 세계(Isolated World)**에서 실행된다. 같은 탭 안에 "서로 다른 JS 실행 환경 두 개"가 동시에 존재하는 구조:

- **공유됨**: DOM 트리(같은 `<video>` 엘리먼트), 실제 렌더링 결과. 한쪽에서 `el.play()`를 부르면 진짜로 재생된다 — 메서드 호출/DOM 조작은 실제 브라우저 내부 구현을 거치기 때문에 어느 세계에서 부르든 실제 효과가 동일하다.
- **공유 안 됨**: 전역 변수(`window.foo`), 함수/클래스 정의, 그리고 **내장 객체의 프로토타입**(`HTMLMediaElement.prototype` 등 — 각 세계가 자기만의 복사본을 가짐).

### 왜 `Object.defineProperty`로 속성을 잠가도 다른 세계엔 안 먹히는가
`Object.defineProperty(el, "volume", {...})`처럼 속성을 재정의하는 건 **그 재정의를 실행한 세계의 프로토타입/객체에만** 적용된다. 격리된 세계(우리 확장)에서 아무리 `.volume` setter를 가로채도, 페이지 자신의 스크립트(메인 세계)는 자기 세계의 원본 `HTMLMediaElement.prototype`을 그대로 쓰기 때문에 전혀 영향을 못 받는다. 겉보기엔 "제대로 짠 코드"인데 실제로는 아무 효과가 없는, 아주 찾기 어려운 종류의 버그였다 — 콘솔에 에러가 안 나고, 로직도 틀린 데가 없어 보이니까.

### 왜 `chrome.*` API는 메인 세계에 아예 없는가
보안 경계다. 웹페이지 자신의 스크립트가 `chrome.tabs`, `chrome.storage` 같은 확장 API를 쓸 수 있으면, 아무 웹사이트나 사용자가 설치한 확장의 권한을 가로채 쓸 수 있게 된다. 그래서 Chrome은 `chrome` 객체 자체를 메인 세계에는 노출하지 않는다(`typeof chrome === "undefined"`). 이게 **왜 콘텐츠 스크립트를 하나로 합칠 수 없는지**의 근본 이유 — `chrome.runtime` 메시징이 필요한 코드와 페이지의 속성을 가로채야 하는 코드는 각자 다른 세계에 있어야만 자기 역할을 할 수 있다.

### 해결 패턴: 두 스크립트 + postMessage 다리
1. 확장 API가 필요한 코드는 격리된 세계(기본값)에 그대로 둔다.
2. 페이지 자신의 동작을 가로채야 하는 코드만 따로 파일을 빼서, `chrome.scripting.executeScript({..., world: "MAIN"})`로 **메인 세계**에 주입한다.
3. 메인 세계에는 `chrome.runtime`이 없으므로, 두 스크립트는 **`window.postMessage`**(일반 웹 표준 API, 어느 세계에서도 쓸 수 있음)로 서로 대화한다. 받는 쪽은 `window.addEventListener("message", ...)`로 듣고, `event.source !== window`와 자체 네임스페이스 마커(`event.data.source`)로 "진짜 우리가 보낸 메시지인지" 걸러낸다.

### 핵심 인과관계: 세계는 파일이 아니라 "주입하는 쪽"이 결정한다
처음엔 "이 파일은 chrome API를 안 쓰니까 격리된 세계로 안 들어가는 거 아니냐"고 생각하기 쉬운데, 이건 인과관계가 반대다. **어느 세계로 갈지는 오직 `chrome.scripting.executeScript` 호출의 `world` 옵션이 결정**한다. 파일 자신은 자기가 어느 세계에 있는지 전혀 모른다. 실제로:
- 페이지 가로채기용 파일을 실수로 `world` 생략(=ISOLATED)하고 주입하면 → 문법 에러 없이 조용히 실행되지만 아무 효과가 없다.
- 확장 API를 쓰는 파일을 `world: "MAIN"`으로 주입하면 → `chrome`이 `undefined`라서 그 즉시 에러로 죽는다.

즉 "이 코드가 무엇을 할 수 있는가"가 아니라 "이 코드를 어느 세계에 넣기로 우리가 결정했는가"가 먼저고, 그 결정에 따라 쓸 수 있는 API가 정해진다.

### 이 버그를 어떻게 진단했나 (실측으로 가설 검증)
"볼륨이 잠겨야 하는데 왜 계속 튀지?"를 추측만으로 풀지 않고, 실제 사용자의 브라우저(Claude in Chrome 자동화)에 직접 자바스크립트를 주입해서 두 가지를 비교 테스트했다:
- 페이지와 같은 세계(main world)에서 잠금 코드를 실행 → 완벽하게 차단됨(확인).
- 그런데 실제 확장(격리된 세계)에서는 여전히 튐 → 두 결과가 다르다는 사실 자체가 "세계가 다르다"는 가설을 뒷받침하는 결정적 증거가 됐다.

### 다른 곳에서도 마주칠 같은 패턴 (개발자 지망자가 알아두면 좋은 전이 지식)
"두 개의 실행 환경이 있고, 그 경계를 메시지로만 넘을 수 있다"는 구조는 프론트엔드 전반에서 반복된다:
- **Web Worker**: 메인 스레드와 워커 스레드는 완전히 분리된 환경 — `postMessage`로만 통신 가능(여기와 정확히 같은 API).
- **iframe (cross-origin)**: 부모 창과 iframe도 서로 다른 실행 환경 — `window.postMessage`가 표준적인 통신 수단.
- **React Server Components**: 서버 컴포넌트와 클라이언트 컴포넌트("use client" 경계)도 비슷한 개념 — 서버 쪽 코드는 브라우저 API를 못 쓰고, 클라이언트 쪽 코드는 서버 전용 리소스(DB 커넥션 등)에 직접 접근 못 한다. "이 코드가 어느 쪽에서 실행되는가"가 코드 내용이 아니라 파일 위치/지시어("use client")로 정해진다는 점도 여기와 같은 인과관계 구조다.

이런 "경계"를 만났을 때 첫 반응은 "왜 내가 방금 만든 값/객체가 저쪽에서 안 보이지?"인데, 원인은 대부분 로직 버그가 아니라 애초에 서로 다른 실행 환경이라 그렇다는 걸 의심해보는 게 진단 속도를 크게 줄여준다.
